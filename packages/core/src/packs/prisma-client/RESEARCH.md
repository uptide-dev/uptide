## How the compiler sees Prisma

`@prisma/client`'s published types are one line in both majors: `export * from '.prisma/client/default'`
(D6, D7). Every type a consumer compiles against (`PrismaClient`, the `Prisma` namespace, the
constructor options) is **generated** by the `prisma` CLI into `node_modules/.prisma/client`
(`prisma-client-js`) or into the repository (`prisma-client` with `output`). Consequences:

- The type diff `check` runs on `@prisma/client` has nothing to diff: it reports `no usages found`
  for `@prisma/client` in every repository below (BearStudio, jqlang measured with this checkout's
  build). The 4403 "removed" exports `packs/queue.json` counts are `runtime/library`, an entry
  point user code rarely imports.
- The generated client is from the installed CLI. Linking `@prisma/client` 7 next to a 6-generated
  client gives diagnostics no real upgrade has: `packs:truth` reports TS2305 `has no exported member
  'PrismaClient'` at every `import … from '@prisma/client'` (a linked copy no longer reaches
  `.prisma/client`), and TS7006/TS7031/TS2339 wherever the generated types fell back to `any`
  (bcgov: 130 such diagnostics). A real 7 install runs `prisma generate` at 7, after which none of
  them exist. They are never ground truth (see below).
- The compiler-visible 7 changes (TS2554/TS2345 on a constructor without `adapter`, TS2353 on
  `datasources`/`datasourceUrl`, TS2339 on `$use`/`$metrics`, TS2694 on `Prisma.Middleware`, all
  confirmed by probe X) appear only in a client generated by the 7 CLI. `check` runs no generator,
  so this pack finds those sites in source with `detect`, the way the compiler would report them
  after `prisma generate`. Engine follow-up (not in this pack): let `check` compile against a client
  the target CLI generated in an isolated copy.
- Most of the upgrade is outside TypeScript anyway: `schema.prisma`, `package.json`, the
  environment.

## Release group, companions, new dependencies

- **`prisma` is a release-group member**, not a companion. Evidence: G, "Update packages": "you
  need to update both the `prisma` and `@prisma/client` packages"; R (7.10.0) speaks of "a matching
  Prisma 7 CLI"; M: both publish exactly the same version list (6.19.0 … 7.10.1), and neither
  depends on the other (`@prisma/client` peers on `prisma: "*"`, optional), so no dependency edge
  would move the CLI. Source URL: the pinned guide.
- **Installed driver adapters** (`@prisma/adapter-pg`, `-neon`, `-planetscale`, `-d1`, `-libsql`,
  `-better-sqlite3`, `-mariadb`, `-mssql`, `-ppg`) are release-group members too: M shows each
  published at every client version and depending on `@prisma/driver-adapter-utils` at its own
  exact version; R0 ("Driver Adapter naming updates") renames their classes at 7.0.0, and A confirms
  it (6.19.3 exports only `PrismaBetterSQLite3`/`PrismaNeonHTTP`/`PrismaD1HTTP`, 7.10.1 only the new
  names). A 6 adapter left next to a 7 client is a combination Prisma never published. Source URL:
  the 7.0.0 release notes. This is the weakest companion evidence in the pack (no page says "keep
  the adapter at the client's version"): an open question in the pull request.
- **`@prisma/instrumentation` is not a member**: the v7 tracing page installs it `@latest`, and it
  depends on neither the client nor the CLI. It stays where it is, and `check` names it.
- **Adapters the upgrade adds are new dependencies**, not companions: an upgrade from 6 without an
  adapter must add one (`@prisma/adapter-pg` for PostgreSQL, …) and its driver. Uptide never adds a
  dependency (UPT-126: the agent cannot change dependencies), so `client-adapter` is assisted and
  its guide says which package the owner adds. Ground truth `with` lists only packages installed
  before the upgrade (`prisma`), never an adapter the upgrade added.

### Rewrites

None. Each candidate that is 1:1 (dropping `--skip-generate`/`--skip-seed`, dropping
`engineType`, `runtime/library` → `runtime/client` when no missing export is imported, an import
of a renamed adapter class) has at most one real site in the ground truth below, and a rewrite with no
real site runs assisted anyway (UPT-48, `unexercised`). So the code would ship and never run. Add
the rewrite together with the first ground-truth repository that exercises it.

## Detection scope

- TypeScript/JavaScript: every file of the workspace's TypeScript project (`projectFiles`, as the
  redis pack reads wrapper modules) plus importing files, because `check` finds no usages of
  `@prisma/client` (above). A file is read only when its text names `PrismaClient`, `$use`,
  `$metrics`, a Prisma adapter or a Prisma entry point. `new PrismaClient(...)` counts only where
  `PrismaClient` is imported or required from `@prisma/client` or from a module path that ends in
  `/client` or names `prisma`/`generated` (a generated client); a local `PrismaClient` (a jest mock)
  is never a site (fixture `client-adapter` line 9).
- `schema.prisma` and any `*.prisma` file of a multi-file schema, `package.json`, `prisma.config.*`,
  `.nvmrc`/`.node-version`: the pack's inventory.
- Fixtures for package.json and schema files follow sentry-node and the typescript pack: the file
  named by `filename.txt`, with `// @uptide` markers (comments in a Prisma schema; ignored by the
  line-based package.json detectors).
