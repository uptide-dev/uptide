# `uptide init`

For someone who wants Uptide to run on a schedule in their repository's own GitHub Actions.
It writes two files at the repository root and does nothing else: no commit, no push, no
network. `uptide init --help` lists the flags.

```sh
npx uptide init --dry-run    # print the files and the pull request text
npx uptide init              # write them
```

| File | What it is |
| --- | --- |
| `.github/workflows/uptide.yml` | The workflow: on a weekly schedule and on demand, it installs your dependencies and runs the Uptide Action. |
| `uptide.yml` | The settings, with a comment on every field. See [uptide.yml](../config.md). |

These are the files of the "Add Uptide" pull request the Uptide GitHub App opens when a
repository is connected. Both are generated by the same function from the same facts, so
`uptide init` and the App write the same bytes for the same repository. The function is
published as `uptide/onboarding`, with its types:

```ts
import { generateOnboarding, repoFacts } from 'uptide/onboarding';

// files: package.json, the lockfile (its first 64 KB is enough), .nvmrc, ... by root path;
// ONBOARDING_INPUTS lists them. Throws OnboardingRefusal, with .reason, instead of
// generating files that would not work.
const { files, prTitle, prBody } = generateOnboarding(
  repoFacts({ slug: 'owner/name', defaultBranch: 'main', files }),
);
```

It holds the generator only: no analysis engine, no network, no file system and no Node
globals, so it bundles for a browser as well as it imports under Node, Vitest or Turbopack.
Its one dependency, `yaml`, is installed with it. What reads a checkout from disk is a
separate entry, for Node only:

```ts
import { loadUptideConfig, snapshotFromDisk } from 'uptide/onboarding/node';

const loaded = loadUptideConfig(dir); // the nearest uptide.yml, or undefined
const facts = repoFacts(snapshotFromDisk(dir, { slug: 'owner/name', defaultBranch: 'main' }));
```

## What it reads

Only files at the repository root (the Git top level):

- **Package manager and version**: `packageManager` in package.json, and the lockfile
  (`package-lock.json` or `npm-shrinkwrap.json`, `pnpm-lock.yaml`, `yarn.lock`, with
  `.yarnrc.yml` for Yarn Berry).
- **Node version**: `.nvmrc`, then `.node-version`, then `.tool-versions`, then `volta.node`,
  then `engines.node` in package.json (the first of Node 24, 22 and 20 that satisfies the
  range, else the newest other release that does).
  With none of them, Node 24.
- **Workspaces**: `pnpm-workspace.yaml`, or `workspaces` in package.json.
- **Repository and default branch**: the `origin` remote (`owner/name`, for the schedule) and
  its default branch.

## The workflow it writes

- Triggers: the schedule from `uptide.yml`, and `workflow_dispatch` with two inputs, `mode`
  (`list`, `check` or `fix`) and `package` (one dependency, or empty for every dependency
  `uptide.yml` allows). A scheduled run uses mode `fix`.
- Permissions, and nothing else: `contents: write` (push migration branches),
  `pull-requests: write` (open draft pull requests), `id-token: write` (prove to Uptide that
  the results JSON comes from this workflow).
- Every action is pinned to a full commit SHA, with the release it came from in a comment.
- The checkout keeps no token in `.git/config` (`persist-credentials: false`).
- `actions/setup-node` with the detected Node version and the package manager's cache. When
  package.json declares `packageManager`, Corepack runs it: a pinned Corepack is installed
  first, because Node 25 no longer bundles one and the copies in Node 20 and 22 reject newer
  pnpm and Yarn releases. A pnpm repository without `packageManager` gets `pnpm/action-setup`
  with the major version its lockfile implies.
- The install never changes the lockfile and runs no dependency's install scripts:

  | Package manager | Install |
  | --- | --- |
  | npm | `npm ci --ignore-scripts --no-audit --no-fund` |
  | pnpm | `pnpm install --frozen-lockfile --ignore-scripts` |
  | Yarn classic | `yarn install --frozen-lockfile --ignore-scripts --non-interactive` |
  | Yarn Berry | `yarn install --immutable --mode=skip-build` |

- The Uptide Action, with `uptide.yml`, the mode, the package and
  `secrets.ANTHROPIC_API_KEY`. The key is given to that step alone; with `llm.enabled: false`
  it is not passed at all. The Action is `action.yml` at the root of
  [uptide-dev/uptide](https://github.com/uptide-dev/uptide), released with the CLI's version
  tags and pinned by the commit of a release tag. Until the release that ships it, `init` says
  the workflow cannot run yet.

## When it refuses

It writes nothing, and says why, when the files would not work:

| Repository | Why |
| --- | --- |
| No package.json at the root | Uptide works on JavaScript and TypeScript repositories. |
| No lockfile | Uptide installs exactly what the lockfile pins. |
| Bun (`bun.lock`, `bun.lockb` or `packageManager: bun@...`) | Not supported yet. |
| `packageManager` and the lockfile disagree | pnpm declared with a `package-lock.json`, Yarn 4 with a classic `yarn.lock`, and so on. |
| Several lockfiles and no `packageManager` | Nothing says which one is used. |
| `package-lock.json` with lockfileVersion 1 | Uptide needs npm 7 or newer. |
| Yarn Plug'n'Play | Uptide reads installed packages from `node_modules`. |
| No way to tell which pnpm or Yarn Berry to run | Set `packageManager`. |
| `engines.node` that no current Node release satisfies | Add an `.nvmrc`. |
| `llm.provider` other than `anthropic` in an existing `uptide.yml` | The workflow passes only `ANTHROPIC_API_KEY` for now. |

## Running it again

An existing `uptide.yml` is never rewritten: `init` reads it and writes the workflow from its
settings. That is how a changed `schedule` reaches the workflow. An existing workflow that
differs from what `init` generates is left alone unless you pass `--force`; compare first
with `--dry-run`.

## After it

1. Review the two files, commit them on a branch and open a pull request.
2. For assisted fixes, add the repository secret `ANTHROPIC_API_KEY`
   (`gh secret set ANTHROPIC_API_KEY`). Without it, Uptide applies rule-based fixes only.
3. Once the workflow is on the default branch it runs on its schedule, and from the Actions
   tab with Run workflow.

To remove Uptide, delete both files and the secret.

Exit codes: **0** files written (or printed with `--dry-run`), **2** nothing generated (the
reason is printed), an existing workflow differs and `--force` was not passed, or
`uptide.yml` is not valid.
